# NaiLink 重载完成确认

用户的 v0.10.1 真机截图显示“重载请求超时”，随后只读 API 为 `authorized=true, running=true, modified=false`，AdZero 为 `recovery_required`；适配器记录 218,844 个域名，后端为 144,858。规则数量不同说明不能仅将该 API 输出当作本批规则已经生效。

## 原因与 v0.10.2 修复

NaiLink 0.6.30 的 LuCI 网关有 30 秒响应头期限。原生 `run(dry:false)` 使用独立上下文，网关超时后，内核重载仍可能继续。旧版保留适配器日志并阻止再次修改，但外层规则事务仍可能开始恢复来源、重建旧后端，导致后端与仍在加载的代理规则不同步。

v0.10.2 保留现有四代理接入方式，仅修复 NaiLink 请求确认及外层事务边界：

1. 提交前保存恢复记录，只提交一次原生重载请求。
2. DAT 文件单独变化时，DNS 配置文字可能完全相同，原生 `modified` 也可能一直为 false。此时通过官方 `updateDns` API 保存同一段文字，使选中配置版本递增，再观察到 `modified=true`。不改 SQLite、账户或密钥，不更改 DNS 语义。
3. 超时后进入“确认代理重载”阶段，继续最多约 60 秒的只读核对。查询本身有 5 秒期限，防止忙碌数据库使每次核对再等待 30 秒。
4. 必须同时满足：本次有配置版本状态变化依据，原生 running=true/modified=false，健康接口的内核初始化、监听、DNS 和路由恢复均已就绪，选中 DNS/路由仍与本批目标一致，自有文件和后端输入指纹未变。缺少任何一项都不认定成功。
5. 仍未确认时保留本批来源、后端和适配器日志，不立即回滚，不再发第二次重载。后台定期核对，在证据齐全且来源/个人策略未被外部修改时完成原事务。页面重新检测后，已匹配的待应用选择会清除。

正常收到成功回执的流程保持原样。明确的 GraphQL 错误继续走恢复流程；传输中断或未收到完整响应则保守保留。PassWall、OpenClash、Nikki 没有改用新的 DNS 架构，也没有新增运行依赖。

同时修复了并发诊断冲突：旧实现使用固定的 GraphQL 临时文件名，多条 root 诊断与后台请求可能互相删除文件。隔离真实网关的 12 次并发读取复现了错误；新文件名按临时 LuCI 会话隔离，每条请求只清理自己的文件，不影响重载回执。

## 旧版遗留状态与升级

旧日志没有上述“本次配置版本变化”证据；仅凭当前 running/modified 或等待时长无法补造证据。旧版未确认请求需要先通过 NaiLink 原生服务重启，让旧进程的请求不可能继续提交，再由升级器调用旧版正常关闭恢复。重启会短暂中断代理；不要删除 adapter.json、来源事务或操作锁。

先执行 `/etc/init.d/daed restart`，待 NaiLink 页面恢复并且 `/usr/libexec/adzero/adapter nailink-status` 授权正常后，再运行 v0.10.2 安装器的 `--upgrade`。如果旧版恢复仍失败，安装器停止并保留备份，不强制覆盖。

## 验证边界

隔离测试分别覆盖真实 NaiLink CGI 的 30 秒期限、实际 API 的同文 DNS 版本递增、延迟重载回执，以及版本、内核就绪、外部文件或配置变化的拒绝条件。延迟内核和服务清单使用夹具，不等同于真实 ARM 路由器重载或 LAN 广告过滤验收。此修改解决错误确认和并发恢复，不承诺大规则库的实际内核重载耗时已经缩短至固定秒数。
