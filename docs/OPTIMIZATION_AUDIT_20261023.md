# 广告过滤与 DNS 优化审计（2026-10-23）

基线为 v0.15.6；本轮改进进入 v0.16.0。检查了规则下载与缓存、规则匹配、DNS 适配、观察统计、RPC、界面和已有验证记录。没有登录或修改用户路由器，做了少量固定公开域名的只读 DNS 测量；运行信息由用户回传。

## 当前表现

| 检查 | 结果与含义 |
| --- | --- |
| Windows 直接向路由器查询 A 记录 | 八次 UDP 应答中七次为 2.91–3.69 ms，一次 Google 查询为 20.46 ms，紧接的同域查询为 3.38 ms |
| 广告测试域名 doubleclick.net | 两次 UDP 返回 NOERROR、零答案；本轮没有暂停对照，不能据此计算整体拦截率 |
| TCP DNS | 八次尝试未在两秒内完成；另一次单独 TCP 连接探测在三秒内未建立连接 |
| 用户回传状态 | v0.15.6，当前接入 NaiLink，无活动操作，系统有 TCP 53 监听；不是活动 PassWall 的现场 |

这些不是清空缓存后的严格冷／热测量。少量 UDP 样本已较快，不能宣称更换公共 DNS 就能更快，也不能用 NOERROR 证明答案或完整网站连接正确。TCP 连接问题还需区分客户端、NaiLink 接管及防火墙路径；不能把监听存在或历史 SIGCHLD 缺陷当作本次原因。

## 本轮已实现

- **真实应答耗时**：复用现有抓包，不额外发测速请求。用请求和应答的抓包时间差计算，正常正应答、已命中规则且收到拦截应答分别汇总；不拿快速拦截拉低正常解析平均值。显示慢应答（至少 500 ms）及 15 秒内未观察到应答数量。
- **准确的统计范围**：无有效样本时显示横线，清零、接入或配置变化后开启新周期。检测流量、重复包、错误时间戳不混入延迟。未观察到应答可能来自采集遗漏，不直接判定为网络失败；TCP 连接未建立时也不凭空算作已观察 DNS 查询。耗时不含客户端本地缓存命中或完整 TCP 握手，不等于上游纯耗时或缓存命中率。
- **大规则库查询**：对已排序的有效产物，按域名和真实父域做二分查找，保留外层实际拦截范围、个人放行优先及精确匹配模式，不额外建立常驻索引。25 万条规则、十二次混合查询的原生开发测试从约 4.5 秒降为约 0.27 秒，包含解释器启动和数组构造。这是规则查询测试，不是用户 DNS 提速倍数。
- **规则选择提醒**：同时选择 HaGeZi Light、Normal、Pro 中多项时提示覆盖高度重叠，便于保留一项；仅提示，不替换已有选择。规则数与拦截率分别看待。
- **查询范围修正**：单纯 hosts 后端、没有提供后缀过滤的代理时，不再把父域误报成覆盖所有子域的拦截规则。

原有订阅缓存、去重、个人名单、批量应用、手动校验、代理引擎保留和失败恢复继续使用。没有改动生产 DNS 上游、TTL、缓存容量、节点、DHCP 或防火墙，没有新增运行依赖。

主要修改：[observe-lib.uc](../luci-app-adzero/root/usr/libexec/adzero/observe-lib.uc)／[observe.uc](../luci-app-adzero/root/usr/libexec/adzero/observe.uc) 统计，[policy-lib.uc](../luci-app-adzero/root/usr/libexec/adzero/policy-lib.uc)／[policy.uc](../luci-app-adzero/root/usr/libexec/adzero/policy.uc) 查询，[source-lib.uc](../luci-app-adzero/root/usr/libexec/adzero/source-lib.uc) 规则分组，[overview.js](../luci-app-adzero/htdocs/luci-static/resources/view/adzero/overview.js)／[overview.css](../luci-app-adzero/htdocs/luci-static/resources/view/adzero/overview.css) 展示与样式缓存版本；对应测试和原生采集验证同步补充。

## 值得增加的功能

| 优先级 | 功能 | 收益与实施条件 |
| --- | --- | --- |
| 先做 | **命中来源解释** | 显示具体名单、个人规则、父域范围与生效版本。必须关联当前生效产物，不能拿新下载但未应用的列表冒充当前来源 |
| 先做 | **临时放行** | 十分钟／一小时／本次会话放行，到期恢复；保留永久放行，明确范围与失败恢复 |
| 先做 | **规则组合与更新概况** | 轻量、均衡、增强模板，显示更新结果、生效时间与重复覆盖；复用批量应用与后端已有调度，避免两套调度重复下载 |
| 随后 | **上游测速与组内备用切换** | 分开检测国内、国外路径的延迟、失败与稳定性，国外测试必须走实际代理。先手动检测；自动切换需连续失败确认、退避和冷却，避免抖动反复重载 |
| 随后 | **缓存状态与适度调优** | 优先复用原生统计接口，按内存评估容量；不凭低延迟推断缓存命中，不用强拉长 TTL 保存旧地址 |
| 随后 | **DoH／DoT 上游** | 逐引擎验证协议、证书、引导解析、代理路径和关闭恢复；配置框接受 URL 不等于协议生效 |
| 后续阶段 | **CNAME 别名过滤** | 补上第一方域名指向追踪域名的覆盖；需要真实 DNS 响应过滤，不能让只读观察器修改回答或把别名命中记成成功拦截 |
| 后续阶段 | **设备策略、有限查询日志、本地域名重写** | 为电视、手机、办公设备分开控制；验证多网段、IPv6、身份变化和保留时长，默认保持低记录量 |
| 后续阶段 | **标准代理能力接口** | 通过实际 TCP／UDP／DNS 出口能力扩展兼容，薄适配器负责发现与接入，减少未来对各插件源码的依赖 |

建议先做“来源解释＋临时放行＋上游检测”，再做备用切换与协议扩展。CNAME 与统一缓存需要单独设计 DNS 处理层，不能夹在一次小版本里切换现有工作链路。

## 参考依据与验证

[AdGuard Home 配置文档](https://github.com/AdguardTeam/AdGuardHome/wiki/Configuration) 提供并行上游、备用解析和缓存等参考能力；上表区分了已实现的观察统计与计划中的真正解析调度。[AdGuard DNS filter](https://github.com/AdguardTeam/AdGuardSDNSFilter) 需要相应过滤语法，不能删掉例外和修饰符后声称完整兼容。[dnsmasq 手册](https://thekelleys.org.uk/dnsmasq/docs/dnsmasq-man.html) 说明缓存容量、过期缓存和 TTL 调整有取舍，不能只选一个大数字当作通用提速方案。

DNS 过滤不保证清理网页空白、同域视频广告或应用自己的加密 DNS。不以拦截数量增长代替用户体验提升。验证见 [本地验证](LOCAL_VALIDATION.md)，使用见 [观察统计](OBSERVATION.md)、[规则管理](RULE_SOURCES.md)、[DNS 设置](DNS_SETTINGS.md)。
