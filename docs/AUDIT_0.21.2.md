# v0.21.2 候选 DNS 预检与代理切换审计

## 已核实的问题

实际任务先通过新 DNS 计划的 `dns-check`，随后在 `routing-check` 返回 `dns_passwall_mode`。`sources.uc` 会把 DNS 有效配置的改变纳入 `routing_changed`，但旧控制器没有把计划传给第二次预检，后者重新读取旧 UCI DNS。国外从并发改为单一因此仍被旧国外并发设置阻止。预检失败发生在事务提交之前，不能把草稿显示成已生效。

同时，接入卡优先采用观察器的旧 `connection`，只检查该样本的 `confirmed`，没有与当前活动代理核对。实际运行 PassWall、旧接入为 NaiLink 时，页面会误称 NaiLink“规则已同步”。

## 修改与保护

| 文件 | 修改 |
| --- | --- |
| `adapter.uc` | DNS 与路由预检共用候选计划解析；可选计划约束目标开关并仅改变进程内预检上下文。 |
| `ctl` | 批量应用的路由预检携带同一计划；保留原事务、冲突检查、恢复与代理迁移逻辑。 |
| `overview.js` | 核对活动代理、已应用接入和观察样本；待同步时显示真实目标与兼容提示，保留关闭保护的操作，不显示旧设备检测为新接入通过。 |
| `test_routing.py`、`test_view.cjs` | 候选预检与完整迁移、真正不兼容／目标冲突、同批关闭严格模式和分流、旧观察与多代理显示回归。 |

没有更换代理 DNS 引擎、自动降级国外并发、修改规则容量或新增运行依赖。未执行用户草稿，未部署开发补丁到路由器。

## 验证

修复前四个候选预检用例中的三个在原生 OpenWrt ucode 下失败；修复后均通过。不兼容国外并发仍拒绝。完整控制器夹具从已停止的 NaiLink 迁移到 Xray PassWall，仅重载一次 PassWall、保持旧核心停止、无需重建过滤后端，广告规则仍在。

计数、同一源码摘要、三套 SDK 和交付检查见[验证摘要](evidence/v0.21.2/summary.json)。服务与 DNS 运行集成测试位于私有环境，不证明用户实机代理迁移或 HTTPS 已恢复。公开证据仅含合成测试，不包含路由器配置、订阅或私密日志。
